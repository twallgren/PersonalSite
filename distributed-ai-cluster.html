Running a 235B model across three MacBooks

Three second-hand M1 Max MacBook Pros, cabled into a Thunderbolt ring, pooling 192GB of unified memory to run a model that fits on none of them. It works — but only after patching MLX, after three confident conclusions turned out to be wrong, and after finding that the library had been silently dropping a layer the whole time. Most of those patches are upstream now, so the path is shorter than the one described here.

01

Start here — if you are going to try this

The one thing
Everything here came down to one number not dividing by three. Tensor parallelism said so and refused to run — an assumption in Python, worth about 500 lines to remove. Pipeline said nothing and quietly dropped a layer or two instead. Neither limit was real; only one of them told you.

Twelve rules, in the order I wish I had learned them. Each one links to the reasoning behind it in the appendix at the end — the rest of the page is the story of how they were arrived at, which you do not need in order to use them.

Node count Three nodes is fine. Budget the patching effort, not a fourth machine. Hardware Prefer desktop Macs to laptops. Interconnect On Thunderbolt 4 there is no RDMA fast path. Model transfer Download once, then copy over the Thunderbolt addresses explicitly. After every reboot Re-detect the Thunderbolt interfaces. Never reapply saved notes. Serving defaults Raise --max-tokens before you use it for anything real. Library version Check whether upstream already fixed it before you debug it. Verification Use top for memory, not ps. Recovery When a node hangs, reboot it — killing the process is not enough. Expectations This buys capacity, not speed.
02

The goal

One model, sharded across three machines. Not three independent model servers behind a load balancer — a single set of weights split into thirds, with every token passing through all three nodes. The three Macs are ai-1, ai-2 and ai-3: 2021 M1 Max MacBook Pros, 64GB of unified memory each, bought second-hand for about $1,250 apiece. Individually they run a 30B model comfortably. Pooled, they have 192GB, which is enough for a 235B-parameter model at 4-bit quantization.

The target was Qwen3-235B-A22B-Instruct-2507-4bit — 123GB on disk, leaving headroom for the key-value cache. ai-1 acts as the controller and the private API endpoint; the other two are compute workers. Admin access runs over Wi-Fi and Tailscale; the model interconnect runs over direct Thunderbolt cabling and nothing else.

What the hardware gives you
Memory you cannot otherwise buy
About $1,250 a machine, so $3,750 for 192GB of unified memory — well under what a single new machine with that much costs, and every node's GPU participates. For models too large to fit anywhere else you own, this is the whole point.
What it does not
Thunderbolt 4, so no RDMA
MLX's JACCL fast path needs Thunderbolt 5 and a direct cable between every pair. The M1 Max has TB4, so the only option is the TCP ring backend — a full round trip through every rank, per token, forever.

That constraint is worth sitting with, because it sets the ceiling on everything that follows. The ring backend is a logical communication algorithm, not a physical cabling requirement — it runs over any IP-reachable network. But it is TCP, it has no remote direct memory access, and each token is a sequential trip around the ring. No amount of configuration removes that.

03

The plan

Cable all three machines into a physical ring — ai-1 to ai-2, ai-2 to ai-3, ai-3 back to ai-1 — so every leg of the ring backend's nearest-neighbour communication has a real one-hop link with no relaying. Closing a loop like that would normally risk a broadcast storm, since macOS's Thunderbolt Bridge has no spanning-tree protection. It is safe here only because the setup tool explicitly tears the bridge down and replaces it with isolated point-to-point links, one per cable, each on its own tiny subnet.

ai-1rank 0controller · API endpoint
ai-2rank 1worker
ai-3rank 2worker

Everything else was scripted from my laptop, so that a node could be rebuilt from scratch without touching it physically: SSH key distribution, disabling sleep, matching Python environments at identical paths on all three, pushing a Hugging Face token, and configuring the Thunderbolt network. The API binds only to loopback on the controller and is reached through an SSH tunnel — nothing about this is exposed to the network.

Launching the cluster

mlx.launch --backend ring --hostfile cluster.json --env MLX_METAL_FAST_SYNCH=1 -- \ python -m mlx_lm.server \ --model mlx-community/Qwen3-235B-A22B-Instruct-2507-4bit \ --pipeline --host 127.0.0.1 --port 8080

That is the finished command. Getting to the point where it ran took considerably longer than writing it.

04

What broke

Twelve failures · expand any one

Almost none of these were interesting distributed-systems problems. They were operating-system behaviour, shell trivia, and one dead cable. That is worth saying plainly, because the hard part of this project was not the parallelism — it was everything underneath it. They are listed in roughly the order they happened; open whichever ones sound like your situation.

Shell
USERNAME is a reserved variable in zsh

Assigning to it does nothing at all — zsh treats it as a special parameter tied to the real system user. A provisioning script that stored the SSH username there silently ignored every --user override and used the login name instead. No error, no warning. Renaming the variable fixed it.

SSH
The controller needs passwordless SSH to itself

MLX's launcher treats the controller as just another host in the list and connects to it the same way it connects to the workers. The key-distribution script only pushed keys outward, so the controller could reach both workers but not itself. Host-key fingerprints need accepting per address, too — the Thunderbolt IPs are separate entries from the hostnames, and a non-interactive script fails rather than prompting.

Networking
Local hostname resolution stops working across networks

The .local multicast DNS names do not cross network segments. Switching my laptop to a different Wi-Fi network for an unrelated reason made all three nodes unreachable, in a way that looked exactly like the cluster being down. Tailscale hostnames work regardless of which network the client is on, so admin access moved there permanently.

Power
Idle machines slept and vanished

An entire-cluster “everything times out at once” episode early on turned out to be three laptops going to sleep. pmset -a disablesleep 1 on each node, applied during provisioning. Later, one node drained its battery to zero while plugged in and hard-stopped, which is when I learned that a drained MacBook needs a physical power-button press to come back.

Permissions
The ring would not connect, and the network was fine

Cluster initialisation failed with a connection error on specific node pairs while others worked. Ping was clean. A raw TCP connection to the same address and port succeeded instantly. The firewall was off. It looked like an upstream bug, and it matched an open issue in MLX's tracker almost exactly.

It was not. Two mundane local causes, both requiring physical access. First: macOS Local Network Privacy was silently blocking the Homebrew Python binary from making same-subnet connections. Apple-signed binaries are exempt — which is precisely why every diagnostic I had run passed. A controlled test settled it: alternating connection attempts to the same peer in the same second, system Python succeeded eight times out of eight, Homebrew Python zero out of eight. Second: one of the three Thunderbolt cables was dead, showing inactive on both ends.

The transferable lesson: when you are checking whether a specific process can reach the network, test with that process. A proxy tool can be exempt from permissions the real one is not.

Transfer
Model copies silently took the slow path

Copying the model between nodes using bare hostnames routed the transfer over Tailscale instead of the direct Thunderbolt link: roughly 170KB/s against the 340MB/s the cable actually delivers, with no error and no indication anything was wrong beyond appearing slow. It happened twice in one session, so I wrote a script that derives the correct point-to-point address by matching subnets on both ends rather than trusting any cached mapping.

Measurement
ps undercounts MLX memory badly

Verifying that a model had genuinely split across nodes meant checking per-node memory. The RSS column showed about 1.6GB per node for a 38GB model — alarming, and completely wrong. Metal-backed unified-memory allocations are not fully attributed to a process's RSS. Measuring with top instead gave 14 / 14 / 13GB, which matched the model. The whole verification depended on picking the right tool.

Tool calling
One trailing newline broke every tool call

Pointing a coding agent at the cluster, every tool call came back as Model tried to call unavailable tool 'bash\n' — with the tool named bash plainly present in the list of available tools. Two candidates: the server was emitting a dirty name, or the client was mangling the streamed response. They have completely different fixes, so the first move was the cheapest test that separates them — call the endpoint directly and print the raw repr of the function name, rather than reading the rendered text.

The server was returning 'bash\n'. GLM emits tool calls with the function name on its own line before the arguments, and the parser captured it with a regex in DOTALL mode that swallowed the newline. The argument keys and values two lines below were already being stripped; only the name was missed.

The part worth remembering is the second bug hiding behind the first. That dirty name gets matched against the tool schema to decide which arguments are strings. 'bash\n' matches nothing, so every declared string argument was handed to a deserializer instead — meaning a string that happened to look like a number would have been silently coerced to the wrong type. The visible failure was a missing tool. The invisible one was type corruption in the arguments, and it would have surfaced much later as something far stranger.

Upstream had fixed this a fortnight earlier, in a commit that has still not reached a tagged release. I found that out after writing my own identical one-line fix. Searching the upstream log first would have cost two minutes.

Download
A finished download that still looked incomplete

The 123GB download reported success and exited cleanly, but seven zero-byte .incomplete placeholder files remained in the cache. They were orphans from an earlier retried attempt — the real, complete files sat alongside them under the same hashes. The way to tell the difference is not to count placeholder files but to check whether any symlink in the snapshot fails to resolve. None did.

Migration
The cleanup that nearly destroyed the work

Moving off hand-edited files and onto the fork branch was the right fix, and it was the closest this project came to losing something irreplaceable. The plan was correct: extract each local patch as a diff, then uninstall the package and reinstall from git. I extracted the patches my notes listed. There was a fourth one, written in a different session and written up in a different document, and I had not read that document yet.

pip uninstall removed the live file on all three nodes at once. Only the pre-patch backup survived, which is precisely the version without the work in it. Then every recovery route came up empty in turn: no compiled bytecode left behind, no Time Machine local snapshots on any node, nothing in the client-side clone but vanilla upstream, no branch or pull request anywhere holding it, and the per-node home-directory git repos exclude the virtual environment — deliberately, since the first commit.

What saved it was a stale scratchpad directory under /private/tmp, left behind months earlier by the session that first wrote the patch. A full copy was still sitting there. Two independent reconstructions of the file then agreed byte for byte, which is the only reason it could be trusted rather than merely hoped over; it is now a real commit, re-verified end to end against the same 72B model as the original.

Two things generalise. Prose describing a patch is not the patch — that file was thoroughly documented and the documentation could not restore a line of it. And do not trust your notes to enumerate your own hand-edits: run find over the installed package for backup files and let the filesystem tell you how many patches you actually have, because a cluster accumulates them from sessions you have forgotten.

Modes
An unsupported mode that hung instead of failing

Forcing pipeline mode on a model whose architecture implements only sharding does not produce an error. It hangs, indefinitely, exactly like the memory fault above. The model loads lazily on the first request, so the “this architecture does not support pipelining” exception is raised on a background worker thread that never signals the HTTP layer — the request simply waits forever for a response nobody is going to send.

Two failures with identical symptoms and completely different fixes is worth a cheap discriminator. This one is deterministic and memory stays flat at a few gigabytes; the leak shows forty to fifty. Checking wired memory tells them apart in seconds, which matters because the recovery for one is a reboot and for the other is switching mode. The underlying gap has since been closed — that architecture now has a pipeline implementation — but a mode an architecture does not implement should still fail loudly rather than wait forever.

Operating
Memory that no process was holding

Requests to one of the mid-sized models began hanging indefinitely — no error, no timeout, nothing in the server log. The hang had a consistent shape across attempts: the first and last pipeline ranks spinning at full CPU, waiting, while the middle rank sat at zero and macOS itself labelled that process stuck.

The ring was fine this time — all three point-to-point links were verified established at both ends during an actual hang, which is what separates this from the interface-mapping failure above. What was not fine was memory. With no inference process running anywhere on the cluster, the three nodes were still holding 43GB, 54GB and 39GB wired out of 64GB installed, against a bare macOS baseline of a couple of gigabytes. The decisive test was to reboot the worst node alone and leave the other two untouched as a control: it fell from 54GB to 2GB, and they did not move. The memory was genuinely orphaned, and nothing short of a reboot released it.

The likeliest explanation is that killing a process whose GPU work has already wedged the driver leaves the driver holding what it had wired — a documented failure mode on this platform, though I have not yet caught a panic log that would confirm it here rather than merely fit it. The operational lesson holds regardless of cause: measure wired memory rather than process memory, and put a ceiling on the key-value cache, since letting it grow unbounded supplies exactly the memory pressure this failure feeds on.

Three conclusions I got wrong

Each was reached with real evidence and written down as settled. Each was wrong. Keeping them on the record, because the reasoning that produced them is the interesting part. The third one is the most useful finding on this page if you run any pipeline-parallel model: the library was silently dropping a layer.
Retracted
Wrong
“Distributed inference over a Thunderbolt ring is inherently slow.”

The evidence: a real request to a 106B reasoning model took over twelve minutes to produce 300 tokens, with all three nodes pinned near 100% the entire time. Not hung — genuinely working, just slow. I wrote it up as the unavoidable cost of pipeline parallelism over TCP without RDMA.

That measurement was taken on a cluster in a corrupted state, and I generalised from it. The same model, correctly configured, now runs at about 18 tokens per second — so those 300 tokens take roughly seventeen seconds rather than twelve minutes. Not a refinement of the original figure: more than forty times off it.

Distributed inference here is slower than a single machine, and the largest models do run at single-digit tokens per second. But that is a property of moving every token around a TCP ring, not the catastrophe one broken measurement implied. The lesson is narrower and more useful than “benchmark carefully”: a number taken from a system you have not yet verified is healthy is not a measurement of the system, it is a measurement of the fault.

Retracted
Wrong
“Point-to-point send and receive is broken on MLX's ring backend.”

The evidence looked strong. Collective operations worked in about 5ms. Sending from rank 2 to rank 1 completed in 0.08s. Sending from rank 1 to rank 0 hung forever — on a link that benchmarked 32KB TCP round trips at 0.32ms. Repeated across runs.

The real cause was a stale Thunderbolt interface mapping. A reboot had renumbered the interfaces, and I had reapplied the old addresses from my notes, putting rank 0's advertised address on the wrong physical interface. Cluster initialisation and every collective still worked, so the cluster looked healthy — only direct send and receive into that one mis-mapped rank failed.

Two things made this genuinely hard to see. MLX enqueues distributed operations on the GPU stream, so a networking misconfiguration surfaced as kIOGPUCommandBufferCallbackErrorTimeout — a GPU error. And the repeated timeouts then wedged the Metal driver, so that afterwards even single-node inference hung with the GPU pinned at 100%. That invalidated other tests I had run in the same window and sent me further down the wrong path. Only a reboot cleared it.

Retracted
Wrong
“These models are running correctly.”

Every pipeline result on this page was checked the same way: launch the model, send a real prompt, read a coherent answer, confirm the memory split three ways. All of that passed. The models were not running correctly.

The shared function that assigns layers to ranks — used by every pipeline-capable architecture, not by anything I wrote — computed its partition by multiplying a per-rank size instead of accumulating a running offset. The code did try to handle an uneven split: it works out the remainder and gives the leftover layers to the low ranks. It just derived each rank's starting offset from the adjusted size rather than from where the previous rank actually stopped, so the ranks disagreed about the boundaries and layers fell through the gap. They were loaded into memory and then executed by nobody.

On this cluster it hit five of the eight models, and how many layers went missing depends on the remainder: one layer for Llama-3.1-8B at 32, Qwen2.5-72B at 80 and GLM-4.6 at 92, but two for GLM-4.5-Air at 46 and for the 235B at 94. The two models that were ever correct, at 27 layers and 48, were correct by arithmetic accident.

It survived months of use because a transformer with one missing middle layer still writes fluent, plausible text. It passed every spot-check I ran, including ones I designed to be strict. The bug was found by code review of an unrelated change, not by any output ever looking wrong — and the fix was verified by brute-forcing the partition arithmetic across thousands of layer and rank counts rather than by reading more completions.

Upstream found and fixed the same bug independently, at almost the same time, in a change neither of us knew the other was writing. Two people looking at that file within weeks of each other after it had been quietly wrong for months is the version-lag lesson from further up this page arriving a second time, in a form I did not expect: it is not only that the fix you need may already exist, it is that the bug you just found may already be someone else's open pull request.

The uncomfortable part is that “it produced a correct answer” was doing much less work as evidence than I thought. A system that degrades into plausible output has no failure signal to notice, so the only honest verification is the arithmetic, checked directly.

What actually generalises
An error's category can be a lie. A GPU timeout meant a networking fault; a clean ping meant nothing about whether the process could connect. In both cases the diagnostic I trusted was measuring something adjacent to the thing I cared about. The fix in both cases was the same: reproduce the failure using the exact component under suspicion, not a convenient stand-in.
05

The constraint that shapes everything

MLX offers two ways to split a model across machines, and they have very different rules.

Tensor parallelism slices individual weight matrices across nodes. It is usually described as the faster of the two, and on a high-bandwidth interconnect it is. That reasoning may well invert here: it synchronises once per projection rather than once per layer boundary, which is many more round trips per token, and round trips are exactly what a TCP ring with no RDMA is bad at. That was a hypothesis for a long time, and it is now measured — see the head-to-head below, which runs the same models both ways. Tensor parallelism also requires that the shapes divide evenly: the number of attention heads and the number of key-value heads must both be divisible by the node count.

Pipeline parallelism assigns whole transformer layers to each node instead. By design it has no divisibility constraint — leftover layers simply go to the first few ranks. The cost is a full round trip through the ring per token. In practice the code that did that splitting got the uneven case wrong for months, which is its own story further down; the constraint was absent from the design and present in the implementation.

I checked four major open models against the tensor-parallel rule at three nodes, and every one failed. The reason is more specific than “the numbers are awkward”. Qwen3-235B-A22B has 64 attention heads and 4 key-value heads. GLM-4.5-Air has 96 and 8. Llama-3.3-70B has 64 and 8. MiniMax-M2 has 48 and 8. Two of those attention-head counts do divide by three — 96 and 48 both do — so the usual shorthand that transformer dimensions are all powers of two is not quite right. But both conditions have to hold, and not one of the key-value counts divides by three. Grouped-query attention has driven that second number down to a small power of two across the board, and a small power of two never divides by three. This is not a property of any particular model; it is a property of how the field designs transformers.

The finding
In stock MLX, three nodes is a genuinely awkward shape — a fourth divides 64 heads, 8 key-value heads, 4096 and 8192 hidden sizes and 14336 and 28672 intermediate sizes, which unlocks a great deal of the ecosystem with no code at all. That is where I stopped the first time, and it was the wrong place to stop — not only because the limit turned out to be removable, but because a fourth machine is not even a general answer. Qwen2.5-72B, the model I ended up running tensor-parallel, has an intermediate size of 29568. Divided by four that is 7392, which is 32 short of a multiple of the quantization group size, so it fails at four nodes. Divided by three it is 9856, an exact multiple of 64. The awkward number was fine on that dimension and the tidy one would not have been.

And for quantized models, a third gate

Head-count divisibility is necessary but not sufficient. Quantized weights are stored in groups — typically 64 values sharing a scale factor — and a shard cannot cut a group in half. So every sharded dimension, divided by the node count, must still be divisible by the quantization group size.

A worked example that fails. DeepSeek-V2-Lite across two nodes passes every head-count check: 16 attention heads, 16 key-value heads, hidden size 2048, all cleanly divisible. It still breaks, on the intermediate size:

The failure, in full

# intermediate_size = 10944, split across 2 nodes 10944 / 2 = 5472 5472 % 64 = 32 # not a multiple of the group size ValueError: [quantize] The last dimension of the matrix needs to be divisible by the quantization group size 64. However the provided matrix has shape (2048, 5472)

This error appears at first inference — after the download, after the load. Checking three numbers in config.json beforehand takes two minutes and saves hours.

Which left the actual problem. Pipeline parallelism has no divisibility constraint and would work fine at three nodes — but at the time, upstream MLX implemented it for only a handful of architectures, and qwen3_moe, the architecture of the target model, was not among them. As shipped, the target model could not be distributed across this cluster by either strategy.

The obvious read is that three was the wrong number and a fourth machine was the fix. That is what I assumed for longer than I should have. But “the library does not implement this” and “the hardware cannot do this” are very different statements, and only the second one is a reason to buy something. So before ordering anything, I went to read why the constraint existed.

06

Two patches to MLX

Both started as edits to files inside the installed package, which any upgrade silently reverts. That is worth stating plainly rather than presenting these as clean contributions — and it was the wrong way to carry them, in a way that later came close to costing me one outright. The model-side patches have since moved onto a fork branch off upstream main, installed editable, so each local change is a commit rather than an edit and upgrading is a merge instead of a silent revert. The core sharding change is still a patched file inside the installed package, because that package ships compiled and building it from source is a heavier commitment than it has so far been worth. It is now open upstream as MLX pull request #4465.

One: pipeline support for two more architectures

The smaller patch. MLX already had a working pipeline implementation for other model families, so this was largely a matter of applying an existing pattern to qwen3_moe and llama: mix in the pipeline behaviour, iterate over only this rank's layers between a receive and a send, then broadcast the final hidden state to every rank before the output norm. Around fifteen to twenty lines each.

One wrinkle was specific to Llama. It computes attention-masking indices at construction time over the full layer list, and those indices become invalid the moment pipelining truncates that list to a single rank's share. Building the masks lazily from the rank's actual layers fixed it, with a fallback for a rank that happens to own none of one mask type.

Verified on smaller models of each family first — an 8B Llama and a 30B Qwen3 — both producing real completions with memory genuinely divided three ways before committing to the 123GB download.

Upstream has since added pipeline parallelism for Qwen3-MoE independently, so that half of the work is now in the library for anyone on a current version — including this cluster, which runs upstream's implementation now rather than mine. Retiring my own patch in favour of it is the right outcome, and also the useful data point: the gap was small enough that someone else closed it within weeks. Treat “the library does not do this yet” as a claim with a short shelf life, and check before you start writing.

Two: uneven tensor-parallel sharding

The more interesting one, and a much larger unlock: it removes the exact-divisibility requirement from tensor parallelism entirely, which applies to every architecture that already supports it rather than to one model family.

The question worth answering first was whether the constraint was real or merely assumed. Reading the source settled it: the only collective operation in the tensor-parallel forward pass sums a per-rank result whose shape is already uniform regardless of how unevenly the input was split. The divisibility check was a simplifying assumption in Python, not a requirement of the underlying collectives. (I confirmed separately, by experiment, that a different collective does require uniform shapes — but that one is only used in pipeline mode, so it was not in the way.)

The core is a helper that distributes a dimension across ranks with the remainder spread over the first few, expressed in units of the quantization group size so no rank ever receives a fragment of a group:

Remainder-aware splitting, in blocks

# dim expressed in whole quantization blocks, so every rank's # slice stays a legal multiple of group_size blocks = dim // block base, extra = divmod(blocks, N) # the first `extra` ranks each take one additional block sizes = [(base + 1 if r < extra else base) * block for r in range(N)] # reduces to the old even split when dim % (N * block) == 0

The genuinely hard part was quantized weights. A quantized layer is not one array but three — the packed weights, the scales, and the biases — and they have different axis lengths, because the weights are packed by bit width while the scales and biases are packed by group size. Splitting each of the three independently at what looks like the same position produces shards that silently do not correspond to each other. The fix scales the split boundaries by the exact integer ratio between each array's real axis length and the logical dimension, so all three are cut at matching logical positions.

There was one more layer to it. Grouped-query attention models share each key-value head across several query heads, so splitting the two independently can leave a rank with a ratio that does not work. The model-side fix distributes whole key-value head groups across ranks, then derives the query and output projection sizes from that grouping — with the output projection's split forced to match the query projection's exactly, since they partition the same dimension on either side of the local computation.

Verified, and its limits
Confirmed on Qwen2.5-72B-Instruct-4bit — 64 heads, 8 key-value heads, hidden size 8192, intermediate 29568, none of which divide by three. It could not run distributed on this cluster at all before the patch. Afterwards it launched with no errors and produced correct answers, with memory at 14 / 14 / 13GB across the nodes. The pattern has since been ported to six more architectures — Llama, Qwen3, Qwen3-MoE and GLM-4-MoE directly, and DeepSeek-V2 and V3 with adaptation, because multi-head latent attention has no separate key-value head count and so distributes heads individually rather than in groups. Four of those are confirmed live at three nodes on head counts that do not divide by three. Two are not: there is no dense Qwen3 model on this cluster to test against, and DeepSeek-V3 at roughly 671B parameters exceeds the pooled memory regardless.

Where this ended up

All of it is now open against the upstream projects, in three pieces plus the core change:

mlx #4465Uneven sharding in the distributed linear layersthe core change
mlx-lm #1863The model-side sharding, six more architecturesblocked on #4465
mlx-lm #1862Pipeline support for Qwen2 and Qwen3-Nextindependent
mlx-lm #1861A checkpoint-loading fix, and DeepSeek-V3.2 onto the shared pipeline baseindependent

Splitting them along those lines rather than by model family was deliberate: one is a pure bug fix against code that already ships, one is new capability with no dependencies, and one cannot merge until the core change does. Bundling them would have mixed “urgent” with “blocked” in a single review. The fourth piece, the layer-drop fix, is not on this list — upstream’s own version of it merged first, so mine was dropped rather than argued for.

What they are not is evidence the outputs were right, which is a separate question and was answered separately. The three reasoning models spend part of that budget on hidden thinking tokens before the visible answer, and those tokens are counted — this is real throughput, not throughput adjusted to flatter it. The patch labels say what was required at the time the work was done; upstream has since absorbed the Qwen3-MoE pipeline support, so most of these now run on the library's own code rather than mine.

The 235B row is the one the project was for. 40 + 41 + 41 comes to 122GB against a model that occupies 123GB on disk — which is the actual proof that it split three ways rather than quietly replicating onto each node. Replication would have shown roughly 123GB on every machine, and would not have fit on any of them. GLM-4.6 pushes that further: 144GB on disk becomes 145GB resident once loaded, spread across three machines that hold 64GB each, which is simply not a thing any one of them can do.

The strategy column is worth reading against that, though it has moved since the work was done. When I started, most of these could not be distributed across three nodes at all; today five of the eight run on stock MLX, because upstream absorbed the Qwen3-MoE pipeline support in the meantime. That is the honest current picture, and it is a better outcome than the one where my patch stays necessary.

Two rows still depend on local changes, and they are the two that make the point. Qwen2.5-72B fails divisibility by three on its head counts and its hidden size, and runs in tensor-parallel mode anyway — the constraint that supposedly rules it out was removed rather than worked around. Llama-3.1-8B needs pipeline support that llama.py still lacks upstream. Neither is a model that happened to fit. That is the difference between three nodes being a limitation and three nodes being a starting point.

The throughput column is the honest headline, and the thing it does not track is file size. Qwen2.5-72B occupies 41GB and runs at 6.4 tokens per second; Qwen3-235B is three times the size and runs at essentially the same speed, 6.0. The 72B is dense, so every parameter participates in every token, while the 235B activates 22B of its parameters at a time — three times the weights, comparable work per token. What throughput tracks is active parameters and round trips. Hold that fixed and the decline is real enough — about 74 tokens per second on DeepSeek-V2-Lite, the sparsest model here, 51 at 30B, 18 at 106B, 6 at 235B, 3.9 at the top end — and that is the cost of moving every token around the ring, not a bug waiting to be tuned away.

The likely reason is that single-stream decoding at batch size one is bound by memory bandwidth rather than arithmetic, so tensor parallelism's per-layer all-reduce — after every attention block and every MLP block — costs more in fixed latency than it recovers by splitting the compute. That inverts the usual advice, and it changes what the sharding patch is for. It is not a performance feature on this hardware; it is a compatibility feature. Qwen2.5-72B was the case that proved it, and it has since gained a pipeline implementation too — which is the better fix, and is why its two columns now sit on top of each other. Two rows sit almost exactly on top of each other in size and tell you what the distribution costs. Qwen3-Coder-Next is 42GB and runs on one node at 10.3 tokens per second; at the time it had neither pipeline nor sharding support anywhere, and needed neither. Qwen2.5-72B is 41GB, one gigabyte smaller, and runs across all three at 6.4. That is not a clean experiment — different architectures, and the 72B is dense where the other is not — but it is the closest pairing available here, and it points the same way as everything else on the page: the cluster is not a faster machine. It is a machine that can hold things no single node here can hold, and you pay for that in latency on every token.

A

The rules, with the reasoning

The long form of section 01

Each of the twelve rules at the top of the page, with why it is there. Most cost me time to learn; a couple cost me a weekend.

Node count
Three nodes is fine. Budget the patching effort, not a fourth machine.

Out of the box, three is an awkward number: tensor parallelism demands that head counts divide evenly by the node count, and grouped-query attention has pushed key-value head counts down to 8 and 4, which never divide by three. Four nodes sidesteps most of it with no code. That is the standard advice, and it is why I nearly bought a fourth machine.

It turned out to be unnecessary. Both limits are software assumptions, and both are removable — pipeline support is about fifteen to twenty lines per architecture, and the divisibility requirement in tensor parallelism came out in one patch that applies to every architecture at once. A missing strategy or a dimension that will not divide is effort, not an exclusion. Price the fourth node against a weekend of reading MLX's source, and decide on that basis rather than assuming the constraint is fixed.

Hardware
Prefer desktop Macs to laptops.

A Mac mini or Studio restarts itself after a power cut. A MacBook that fully drains its battery does not — it needs a physical press of the power button, and no software setting changes that. Mine drained to zero while plugged in, because sustained full-compute draw can exceed what the charger supplies — a 16-inch M1 Max wants something like 96W of USB-C power delivery to hold its own under load, and anything less loses ground slowly enough that you will not notice until the node is gone. Related: FileVault and Automatic Login are mutually exclusive on macOS, because FileVault's pre-boot prompt happens before the OS can read the auto-login preference. So an unattended reboot either leaves the machine encrypted-and-stuck or unencrypted-and-recoverable. Pick deliberately.

Interconnect
On Thunderbolt 4 there is no RDMA fast path.

MLX's fully-connected JACCL backend needs Thunderbolt 5. On TB4 hardware you get the TCP ring backend, which means every generated token makes a full round trip through all the ranks. Direct Thunderbolt cabling still beats 10GbE and costs nothing extra, so cable a physical ring. The ring is safe from bridging loops as long as you let mlx.distributed_config --auto-setup configure it — it disables macOS's merged Thunderbolt Bridge and gives each cable its own isolated point-to-point link.

Model choice
Check the model's numbers before downloading 123GB.

Three gates, all of which must pass: the architecture has to implement the strategy at all; head counts must divide by the node count; and for quantized models, every sharded dimension divided by the node count must still be divisible by the quantization group size, normally 64. Skipping the third gate costs you a full download and load cycle before the error appears. The numbers are all in the model's config.json — it is a two-minute check.

Permissions
Grant Local Network access to your actual Python binary first.

macOS silently blocks same-subnet connections from non-Apple-signed binaries. Homebrew Python is one; ping, nc and system Python are exempt. So every connectivity check you run will pass while the thing that matters fails, and the error you get is a generic connection failure with no mention of permissions. The prompt cannot appear over SSH, so trigger it locally at each machine before you start.

Model transfer
Download once, then copy over the Thunderbolt addresses explicitly.

Each node needs the full model — sharding happens at load time, not download time. Three simultaneous downloads just split one home connection three ways. Download on one node, then rsync to the others across the Thunderbolt links, which run in parallel because they are separate cables. Use the point-to-point IPs, not hostnames: a bare hostname resolves through Tailscale and transfers at roughly a two-thousandth of the speed with no error, no warning, and no obvious symptom beyond seeming slow. This caught me twice in one session.

After every reboot
Re-detect the Thunderbolt interfaces. Never reapply saved notes.

A reboot wipes the runtime network configuration and macOS renumbers the interfaces — what was en2 becomes en3, and the addresses move with it. Reapplying a previously-recorded mapping puts a rank's address on the wrong physical interface, which is a uniquely nasty failure: the cluster initialises fine and all collective operations pass, so it looks healthy. Only point-to-point send and receive hangs. That is exactly what pipeline parallelism uses.

Serving defaults
Raise --max-tokens before you use it for anything real.

The server defaults to 512 tokens per completion. That is fine for a chat reply and silently wrong for everything else — a coding task stops mid-function, a long document stops mid-paragraph, an agent loop stops mid-plan. There is no error; the response just ends and the finish reason says it hit the limit, which is easy to miss when you are reading the text rather than the envelope. I default mine to 8192. While you are there, put a ceiling on the key-value cache too — it is unbounded by default, and an unbounded cache across a long session is a slow build toward the memory pressure described further down.

Size that ceiling per model rather than picking one number. These are identical machines, but what is left after the weights load is not: Llama-3.1-8B occupies 2.2GB a node and leaves about 58GB free, while GLM-4.6 occupies 51GB and leaves about nine. A single cap is therefore both too tight and too loose at once — mine was 8GiB, which made the small models pay avoidable cache misses while handing most of the remaining room to the one model that had caused the memory trouble in the first place. I now derive each model’s cap from its own measured footprint: half of what is left after the weights and an allowance for the OS, which comes out at 16GiB for the models under 20GB a node and 4GiB for the largest.

Two more worth setting deliberately on a cluster this full. --prompt-cache-size defaults to holding ten distinct KV caches in memory, which is generous when your spare headroom is single-digit gigabytes per node — I lowered it to five. And a reasoning model's hidden thinking tokens cannot be turned off by asking it politely in the prompt; that takes --chat-template-args '{"enable_thinking":false}' at launch, using the enable_thinking convention that the Qwen3 and GLM 4.x chat templates share. Asking in the prompt was the first thing I tried, and it did nothing.

Library version
Check whether upstream already fixed it before you debug it.

A pip install gives you the latest tagged release, and on a library moving this fast that can be months behind the branch. My cluster runs 0.31.3, tagged in April. A bug I spent an evening on had been fixed upstream in August — and that fix is still in no tagged release at all, so no amount of upgrading through normal channels would have delivered it.

So search the commit log on main first, not last. And if you are carrying local patches, stop editing files inside site-packages — that is what forces the choice between your changes and upstream's fixes. Fork the repo, put your patches on a branch off main as ordinary commits, and install that branch editable. Upgrading becomes a merge you can read, your patches survive it, and you inherit everything upstream has fixed since the last tag. That is what I should have done at the start.

It works cleanly for a pure-Python package. For a compiled one, where building from source is a much heavier commitment, a patched file under site-packages may still be the pragmatic answer — but then it is the one you have to remember to re-apply, so write down where it lives.

The migration to that arrangement proved the point on the way through. The pip uninstall that preceded it deleted one of the patches outright, because that patch existed only as an edited file and nothing else knew it was there — recovered by luck, from a copy an earlier session had left in a temporary directory. So when you make the move, inventory from the filesystem rather than from your notes: run find over the installed package for .bak files and count them. A patch that is not a commit somewhere is one uninstall away from gone, and you will find out at the worst moment.

Verification
Use top for memory, not ps.

On Apple silicon the RSS column badly undercounts MLX's Metal-backed allocations. It reported 1.6GB per node for a 38GB model, which reads as a catastrophic failure. top -pid <pid> -l 1 -stats pid,mem gave the real figures. Since per-node memory is how you prove a model genuinely split rather than silently replicated, using the wrong tool here means you cannot tell success from failure.

Recovery
When a node hangs, reboot it — killing the process is not enough.

Killing a wedged inference process does not reliably return the memory it had wired for the GPU. That memory stays wired below the process layer, where ps and top’s process list cannot see it, so a node can show almost nothing running and almost no memory free at the same time. On this cluster, with zero inference processes alive anywhere, the three nodes were still holding 43GB, 54GB and 39GB wired out of 64GB. Rebooting one and deliberately leaving the other two alone as a control dropped it from 54GB to 2GB while they did not move — which is what makes it leaked rather than legitimate. Check wired memory, not process memory, and treat a reboot as the recovery step rather than the last resort.

Since capping the cache the hang has not recurred, through five days of repeatedly loading and unloading every model on the list. That is suggestive rather than conclusive — five days is not long to watch an intermittent, load-dependent failure, and there are enough retractions on this page already to be wary of one drawn from a quiet week. What it does support is the ordering: bounding the cache attacks the pressure that precedes the hang, while rebooting only cleans up after it. Do the first, and keep knowing how to do the second.

Expectations
This buys capacity, not speed.

A cluster like this lets you run models that fit on no single machine you own. It does not make them fast. Measured across the same sweep, the best case is 74 tokens per second on a 16B model with only 2.4B parameters active, falling to 18 at 106B and 6 on the 235B, and a 42GB model that fits on one node still only manages 10 — so the ceiling is low even before you distribute anything. If everything you care about fits on one box, buy the bigger box. This is worth doing only for the models that do not fit, and what you get is capability, not speed.

What I would tell someone starting
Read the source before you buy hardware. Test with the real binary. Re-detect, never remember.

The constraint that shaped this project turned out not to be a constraint. Three nodes looked like the wrong number for months, and the fix was framed everywhere as buying a fourth machine. It was about 500 lines of Python standing in for a limit the hardware never had. Check whether the wall you have hit is made of silicon or of someone's simplifying assumption — the second kind you can move.

The harder half is that the same arithmetic failed twice and only announced itself once. Tensor parallelism refused to run and sent me to read its source, which is how the limit got removed. Pipeline accepted the same awkward number, dropped a layer or two, and returned fluent text for months. A system that fails loudly is doing you a favour; one that degrades into plausible output is not, and only the second kind needs you to go and check the arithmetic yourself.

Be clear, too, about what you are buying. This is capacity, not speed — the ability to run something on hardware you already own that would not otherwise fit anywhere. Judged as a fast chat machine it is a bad one. Judged as 192GB of pooled memory, it does exactly what it was meant to.
